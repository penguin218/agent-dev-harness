# 六判据口径与触线动作（quality-gates）

> 本文是 [AGENTS.md](../../AGENTS.md) §4「六判据（代码自优化自查）」的**展开细化**：每条判据说明「怎么看（具体检查动作）」「触线后的动作」「说明式证据示例」。判据名与口径与 AGENTS.md §4 逐字一致；硬性要求以 AGENTS.md 为准，本文只细化检查方法，不新增、不抬高、不降低要求；判据⑥另有「AI 友好日志」附则（非验收硬要求），见下文。

**使用时机**：六判据在任务中出现两次，口径同源、角色不同——

1. **规划阶段**：写入 plan.md「设计考量」小节（[模板](../../templates/task/plan.md) §4）——设计意图，想清「担心什么 → 怎么处理」
2. **进入验证前**：写入任务 README「代码自优化自查」小节（[模板](../../templates/task/README.md)）——落实复核，规划时想的是否真做到、编码中有没有新冒出触线项；**空着视为任务未完成**（AGENTS.md §2 硬要求 4）

**证据口径**（AGENTS.md §4）：说明式，不要求压测或额外量化指标——①②③④ 看代码事实（行数、改了几处、有没有重复），其中①必须提供触碰文件改动前→改后的 `wc -l` 实测表；⑤⑥ 只需列出「做了什么」，不必给压测数据。不涉及的写「本次不涉及」+ 理由。触线本任务不修的，记 [projects/backlog.md](../../projects/backlog.md) 编号跟踪。

---

## ① 尺寸报警

**口径**：文件 >500 行 / 函数 >60 行 / 嵌套 >3 层 / 参数 ≥5 个。

**怎么看**：

- 对本任务每个触碰文件执行 `wc -l`，在 README 自查中列出「改动前 → 改动后」实测行数表，不估算
- 对照该仓 `projects/<repo>/knowledge/size-debt.md` 尺寸债台账，确认触碰文件是否已有超标记录；新超标文件必须当场登记
- 逐个看本次新增/大改的函数：行数是否 >60、条件/循环嵌套是否 >3 层、参数是否 ≥5 个
- 判断标准是**职责**而非单纯长度：**长而单一可接受、短而混杂不可接受**

**触线后的动作**：按「变更原因 → IO/纯逻辑分层 → 复用边界」拆分。触碰已超标文件只有两个合法出路：**当场拆**，或明确写「**使 X 恶化 +N 行**」并更新 `size-debt.md`；禁止用「逼近上限」「不加剧」「净增不多」等模糊话术替代结论。存量巨石不要求在无关任务中硬拆，但只要本任务触碰并使其恶化，就必须按上述口径登记。

**说明式证据示例**：「`parser.py` 180→210 行，最长函数 45 行；已对照尺寸债台账，无触线」；「`handler.js` 510→530 行，使已超标文件恶化 +20 行，已更新尺寸债台账并登记后续拆分」。

## ② 散点数

**口径**：新增同类能力要改几处注册点/分支，>1 即触线。

**怎么看**：数一数——**假设下一个人要新增一个与本次同类的能力，他要改几个文件/几处注册点/几个 if-elif 分支？** 把这些位置逐一列出来。本次自己就是「新增一个同类能力」的人：自己这次改了几处注册点，下一个人大概率也要改几处。

**触线后的动作**：能收敛成单一注册表/映射/约定式发现的，当场收敛；收敛不动的记 backlog，并在自查表写明「**加一个 X 要改 N 处**」——把散点债显性化，让下一个任务不必重新数一遍。

**说明式证据示例**：「新增一种导出格式只需在 `FORMATS` 映射表加一行，1 处，不触线」；「新增一个后端要改 3 处（注册表 / CLI 分支 / 配置模板），本任务收敛不动，记 backlog #12：加一个后端要改 3 处」。

## ③ 重复实现

**口径**：与已有代码同义？同源逻辑写了两份？

**怎么看**：

- 动手写之前先搜：本次要写的能力（解析、校验、重试、格式化……）代码库里是否已有同义实现？用功能关键词和领域名词各搜一遍
- 写完后回看：本次新增的代码里，是否有两段逻辑同源（一处改了另一处也必须跟着改）？
- 特别警惕**同源逻辑分居两个模块各写一份**的情形——它们会各自演化、**各错一遍**，修 bug 也要修两遍

**触线后的动作**：同模块内的直接合并成一份；确实无法共享的（如跨进程/跨语言边界），至少在两侧**注释互指** + 测试同构，并在自查表声明「同源双份，改动需双改」。

**说明式证据示例**：「重试逻辑复用了已有的 `with_retry()`，未新写」；「配置解析在客户端/服务端各一份（跨语言无法共享），两侧文件头注释互指，自查表已声明双份」。

## ④ 扩展性

**口径**：下个同类需求是加数据还是改散点逻辑；受三次法则约束，禁止为假想需求预留抽象。

**怎么看**：问一个具体问题——**下一个同类需求进来，改动形态是「加一条数据/一个文件」，还是「改散在各处的逻辑」？** 前者是好的扩展点，后者是散点债（与②互为表里）。同时检查契约（协议/DTO/存储字段）是否留了向后兼容余地：演进应是**加法**（新增可选字段）而非改既有语义。

**触线后的动作**：收敛扩展点、契约按加法演进。但**方向盘有另一侧**——本判据受三次法则约束（见文末「三次法则边界」）：只对已存在 ≥2 个同类实例的地方做抽象，不为假想需求预留抽象层/配置开关/接口。

**说明式证据示例**：「下个同类校验规则只需在 `rules/` 目录加一个文件，声明式加载」；「响应结构新增 `warnings` 可选字段，老客户端忽略即可，语义不变」；「目前只有一种输出格式，未预留格式抽象层——等第二种出现再抽（三次法则）」。

## ⑤ 分布式

**口径**：多副本下进程内状态/本地文件/定时任务重复执行/回调幂等（不涉及写明理由）。

**怎么看**：**时刻假设每个请求会被随机某个副本接收**，逐项过：

- 有没有依赖**进程内状态/本地缓存/本地文件**？换个副本就读不到的数据，多副本下等于丢数据
- **定时任务/调度器**在多副本下会不会每个副本各跑一遍、重复执行？
- **回调/上报**被任意副本处理，是否都能正确落地？同一回调重复送达是否幂等？
- 长连接（SSE/WS）会话粘在某副本时，别的副本产生的消息怎么送到？

**触线后的动作**：状态入共享存储（DB/Redis）；多副本定时任务加分布式锁；跨副本通知走共享通道（Redis/DB）；处理逻辑做成幂等。本任务不改的记 backlog。

**说明式证据示例**：「状态放共享存储，哪个副本处理都一样」；「定时任务加分布式锁，多副本只有一个实例真正执行」；「回调按业务 ID 幂等落库，重复送达不重复生效」；「本次不涉及——纯 CLI 工具单机运行，无多副本形态」。

## ⑥ 高可用

**口径**：重试退避/幂等/降级不阻断/超时兜底/可观测（不涉及写明理由）。

**怎么看**：逐项过失败路径：

- **失败可恢复吗**——外部调用有没有重试 + 退避？重试的前提操作是否幂等？有没有终态守卫（防止状态被回写覆盖）？
- **非关键路径失败会不会拖垮主流程**——附属能力（采集、上报、统计）失败时是降级继续，还是把主流程一起阻断？
- **有没有超时兜底**——等待外部结果的地方有没有超时？会不会出现期望态永不清除、任务永久卡住？
- **抢占是否安全**——并发领取任务时是否使用行锁跳过已锁记录、CAS 等机制，避免重复执行？
- **可观测够不够**——关键路径日志是否有统一 LOG_TAG 并带关键 ID（任务/会话/请求 ID）？出问题能不能按 ID 把链路串起来？

**触线后的动作**：缺哪补哪；本任务不补的写明理由并记 backlog。

**说明式证据示例**：「采集失败 fail-open 不阻断主流程」；「重试三次退避后放弃并记日志」；「外部调用设 30s 超时，超时置失败态不再无限等待」；「任务领取使用行锁/CAS，避免并发重复执行」；「关键日志统一 LOG_TAG 并带 task_id，可按 ID 串起全链路」；「本次不涉及——纯离线文档生成，无失败恢复语义」。

## 判据⑥附则：AI 友好日志

涉及运行时行为的新代码（后端服务、异步流水线、外部调用、跨副本状态），要求打上便于事后追溯的日志——**目标是仅凭一个业务 ID 就能用日志查询工具把整条链路串起来**（无论查询方是人还是 AI 会话）。非验收硬要求，属判据⑥「可观测」的覆盖内容：plan「设计考量」与 README 自查过⑥时顺带检查。

最小要求：

- **LOG_TAG**：模块级常量前缀（如 `[ORDER_SVC]`），同一链路上的模块用同一 tag——按 tag 一次查询即得该模块全量日志
- **关键业务 ID 必带且同名**：链路主键 ID（如 order_id / task_id / session_id）每条日志都带，且**全链路用同一字段名**——按 ID 检索即可跨模块串起完整链路
- **状态跃迁必打**：状态机每次变更打日志，含前后状态 + 触发原因
- **降级/失败/超时/重试必打**：走非主干路径必打（含原因分类），不吞异常
- **跨服务对齐 trace id**：有链路追踪设施的保留/透传 trace id，用于跨服务关联
- **敏感信息脱敏**：token / password / authorization 只留前几位 + `***`，禁明文（硬红线 3 同源）

不做：不为假想的 debug 需求堆日志（与判据④三次法则同理）；不打刷屏日志——心跳/高频事件降 DEBUG 或按周期聚合，避免淹没关键信息。

## 豁免档

琐碎改动（typo、单行修复、纯文档、纯配置）可豁免六项自查，但**必须留一句豁免声明**（如「本任务仅改文档，豁免」）——**豁免要留痕，不是省略**。落点与 [AGENTS.md](../../AGENTS.md) §2 豁免条款一致：开了任务目录的写入任务 README「代码自优化自查」小节；未开任务目录的写入对应仓 `projects/<repo>/changelog.md` 条目备注。留痕的意义：让复核者一眼看出「这里是想过之后判定豁免」，而不是「忘了做」——两者在文档上必须可区分。

## 三次法则边界

判据④「扩展性」不是「预留越多越好」：它受**三次法则**约束——**只对已存在 ≥2 个同类实例的地方做抽象；禁止为假想需求预留抽象层/配置开关/接口**。只有一个实例时就抽象，是在为想象中的第二个实例设计，而想象通常是错的——等真实的第二个实例出现，会发现当初的抽象轴线根本不对，反而要先拆掉错误抽象再重建。**过度设计与散点债同为缺陷**：散点债是「该收敛的没收敛」，过度设计是「不该抽象的抽了」，自查时两个方向都要看。判断口径：自查表里出现「为将来可能的 X 预留了 Y」而 X 目前实例数 <2 的，按触线处理——删掉预留，等第二个实例出现再抽。
