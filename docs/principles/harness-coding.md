# 五条核心理念展开（harness-coding）

> 本文是 [AGENTS.md](../../AGENTS.md) 头部「核心理念（五条）」的**逐条展开**：每条理念说明「为什么（不这么做会发生什么）」与「在本 harness 中的落点（对应哪个文件/环节）」。硬性要求以 AGENTS.md 为准，本文只解释理念背后的动机，不新增、不抬高、不降低要求。

这五条理念是本 harness 全部规则的源头：任务文档、六判据自查、会话铁律，都是这五条在不同环节的具体化。理解了「为什么」，遇到规则没覆盖到的新场景时，也能照着理念做出一致的判断。

---

## 理念 1：先规格后代码

**一句话原则**：先规格后代码——需求对齐是唯一事前卡点，plan 成文才动手。

**为什么**：不先成文就动手，意味着目标、范围、口径只存在于会话记忆和口头往来里。后果是三连锁：

- **范围漂移无从察觉**——写着写着顺手加了需求外的功能、或悄悄绕开了难点，没有成文的 plan 作对照，谁也说不清「原本要做什么」，范围膨胀与缩水都成了合理化的既成事实
- **返工成本被放大**——需求理解的偏差在对齐阶段纠正只花一句话，在代码写完后纠正要推倒重来；越晚发现越贵
- **会话中断即断片**——Agent 会话随时可能中断，没有成文规格的在途工作，新会话只能靠猜来续作

反过来，「唯一事前卡点」也划定了另一半边界：对齐**之后**的探索、编码、自测、commit、个人/专项分支 push、验证所需内部包发版、预发部署、按 acceptance 自行验证与修复都自主执行，不逐步审批——事前把方向钉死，事后就不需要反复打断。生产部署与 main/master 合入只能由人工执行。

**在本 harness 中的落点**：

- [AGENTS.md](../../AGENTS.md) §2 硬要求 1（需求对齐是唯一事前卡点）与硬要求 2（plan.md 必须含「设计考量」小节）
- 需求对齐时用 [plan 模板](../../templates/task/plan.md) 成文
- 生命周期阶段②「需求对齐」的完成判据（见 [生命周期](../process/lifecycle.md)）：用户确认目标/范围/验收口径，plan.md「设计考量」六项无空项
- 琐碎改动的豁免与留痕：AGENTS.md §2 豁免条款——豁免要留痕，不是省略

## 理念 2：先验收标准后实现

**一句话原则**：先验收标准后实现——acceptance 定义「怎么算通过」，verification 证明「真的通过」。

**为什么**：没有事先成文的 acceptance 就宣称完成，验收标准会随实现漂移——做出什么样，标准就被解释成什么样；「完成与否」从可勾验的客观判定退化为口头之争。更隐蔽的后果是**难验的事被静默跳过**：验收标准若在实现后补写，人会天然只写「已经做到的」，那些应该验但没做到的项根本不会出现在清单上。「不验证的事等于不存在」——代码自优化自查此前被普遍跳过的根因，正是它没有被写成验收项。

acceptance 与 verification 是一对：前者在动手前锁死「怎么算通过」，后者在完成后逐项拿证据证明「真的通过」。只有前者没有后者是空头支票，只有后者没有前者是自说自话。

**在本 harness 中的落点**：

- [acceptance 模板](../../templates/task/acceptance.md)：需求对齐时成文，逐项可勾验，且**必须含 Z 组「代码自优化自查」验收项**，与功能项同权（[AGENTS.md](../../AGENTS.md) §2 硬要求 3）
- [verification 模板](../../templates/task/verification.md)：最终验收前成文，对照 acceptance.md 逐项列「验证方式与命令 → 证据 → 结果」
- 生命周期阶段⑤「验证与回环」（见 [生命周期](../process/lifecycle.md)）：每条验收项按其「验证方式」实际执行，不通过则归因→修复→再验证

## 理念 3：失败不删除

**一句话原则**：失败不删除——验证失败轮次保留。

**为什么**：失败若可删除，任务史就会被整形成「一次通过」的假象：同类问题反复出现时查不到前科，归因失去线索；更危险的是它培养出「先删失败记录再补个通过」的路径，诚实证据的底线从此失守。失败轮次是任务史中信息密度最高的部分——现象、归因、修复，恰恰是知识回流的原材料。

**在本 harness 中的落点**：

- [verification 模板](../../templates/task/verification.md)的「失败轮次记录」节：每次「验证不通过 → 归因 → 修复 → 重新提交/发布/部署 → 复验」逐轮追加，失败记录不得删除
- 硬红线层面对应 [AGENTS.md](../../AGENTS.md) §5 第 4 条「诚实证据」

## 理念 4：每个任务有唯一事实源

**一句话原则**：每个任务有唯一事实源——任务 README 随做随写，断点可恢复。

**为什么**：Agent 会话没有持久记忆，会话随时可能中断、被限流、被切换。若任务状态散落在会话记忆、口头结论、临时终端输出里，中断即断片：新会话不知道进行到哪个子任务、哪些结论已经试错验证过、端口号临时路径这类只在记忆里的信息彻底丢失——只能重做，或者更糟：基于错误的假设续作。「唯一」二字同样关键：状态若写在多处，多处之间必然失同步，读者不知道信哪份，事实源即告失效。

「随做随写」是对「攒到收尾补记」的否定：补记依赖记忆，而记忆恰恰是最不可靠的存储——状态转换的当下就写，才能保证 README 任何时刻都能支撑续作。

**在本 harness 中的落点**：

- [任务 README 模板](../../templates/task/README.md)：任务事实源模板——任务拆分清单（实时更新 + 子任务总结）、探索结论、变更记录、自测证据、恢复锚点
- [AGENTS.md](../../AGENTS.md) §3 会话铁律第 3 条的四项：状态转换即写、关键中间产物即写、恢复锚点常新、子任务完成后用 pathspec 限定小步提交任务 README
- 事实源优先级（AGENTS.md §6）：任务 README 是单任务事实源，仅次于 AGENTS.md；跨任务的知识在收口时回流 `projects/<repo>/overview.md` 与 `projects/<repo>/knowledge/`
- 填好的完整示例见 [minimal-task 示例](../../examples/minimal-task/)

## 理念 5：完成必须有证据

**一句话原则**：完成必须有证据——未执行的验证不得写成通过。

**为什么**：「应该没问题」「理论上会通过」是 AI Coding 最常见的失效模式——实现完成的成就感会诱使人（和 Agent）把「预期会通过」写成「已通过」。一旦允许一次，整个文档体系的可信度即告崩塌：读者无法区分哪些「通过」是实证的、哪些是猜的，verification.md 退化为装饰品，用户验收失去依据，后续会话基于虚假的「已验证」状态续作，错误被层层放大。

证据的标准是**可复核**：命令、cwd、exit code、输出摘要——别人（或下一个会话）照着能重跑出同样的结果。没跑就写「未执行」，跑挂了就写失败轮次，这不丢人；把没跑的写成通过才是本 harness 唯一不可原谅的造假。

**在本 harness 中的落点**：

- [AGENTS.md](../../AGENTS.md) §5 硬红线第 4 条「诚实证据」：未执行的验证不得写成通过；失败记录不得删除或改写
- [任务 README 模板](../../templates/task/README.md)的「自测证据」表：命令 / cwd / exit code / 结果摘要逐条实录
- [verification 模板](../../templates/task/verification.md)：逐项对照表的「证据」列 + 总结论——生命周期阶段⑥「用户验收」以它为依据，未验收不得宣称完成（见 [生命周期](../process/lifecycle.md)）

## 五条理念的关系

按任务时间轴串起来即是 [AGENTS.md](../../AGENTS.md) §2 的流程图：**先规格后代码**（理念 1）与**先验收标准后实现**（理念 2）钉死起点——plan 与 acceptance 成文才开工；**每个任务有唯一事实源**（理念 4）贯穿全程——README 随做随写；**失败不删除**（理念 3）守住中段的验证闭环；**完成必须有证据**（理念 5）钉死终点——verification 拿实证收口。任何一条被绕过，其余四条的效力都会连带失效：没有 acceptance 则证据无处对照，不留失败记录则事实源失真，没有事实源则规格与实现的偏差无从追查。
